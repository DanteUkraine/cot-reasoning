# Chain-of-thought Reasoning

[![License: Apache 2.0](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](https://opensource.org/licenses/Apache-2.0)

[English](README.md) | [Українська](README.uk.md)

**Універсальний фреймворк міркувань для БУДЬ-ЯКОЇ великої мовної моделі**.

**Chain-of-thought Reasoning** — це **модельно-агностична навичка міркувань**, яка
дозволяє БУДЬ-ЯКІЙ великій мовній моделі (LLM) виконувати складні, багатокрокові
завдання, надаючи повний фреймворк мислення.

## ✨ Можливості

- **🧠 Універсальна сумісність**: працює з будь-яким LLM-фреймворком (Mistral Vibe, Claude Code, OpenCode тощо)
- **🎯 Модельно-агностичність**: жодних модельно-специфічних адаптацій не потрібно
- **🔧 Системне міркування**: уможливлює складні інженерні завдання для будь-якої моделі
- **📋 Структуроване виконання кроків**: кожна задача розкладається на виконувані кроки
- **💬 Самодіалог**: прозорий, аудитований процес міркування
- **🔌 Інтеграція інструментів**: безшовна робота з доступними інструментами
- **🎨 Типи мислення**: Analytical, Creative, Critical, Systematic, Ethical, Strategic
- **🌳 Патерни міркування**: Zero-Shot CoT, Few-Shot CoT, Auto-CoT, Tree of Thoughts, ReAct
- **🧭 Екстерналізовані дисципліни міркування**: формалізація контракту, типізовані виводи кроків, контури верифікації, гейти впевненості, покриття edge-кейсів

```bash
npx skills add DanteUkraine/cot-reasoning@cot-reasoning
```

Команда інтерактивна (запитує, до яких агентів встановити). Для скриптів і CI

## 🚀 Використання

### Автоматична активація

Навичка активується на основі свого **опису**, коли запит справді потребує
багатокрокового структурованого міркування:

```
Користувач: "Наш API повертає 500 помилок, досліди і знайди кореневу причину"
→ cot-reasoning активується автоматично (сигнал розслідування інциденту)
→ Генерує структурований потік міркувань у відповідному режимі
→ Виконує з категорійною інтеграцією інструментів
→ Повертає повний аналіз з рекомендаціями
```

Активація гейтована: привітання, прості фактичні питання, однослівні вводи та
тривіальні завдання навичку **не** активують; запити на доменні факти
маршрутизуються до відповідної доменної навички.

### Явна активація

Встановлені навички не мають CLI-прапорців. Щоб викликати навичку явно, назвіть
її в запиті — така формулювання переносима між агентними середовищами (Mistral
Vibe, Claude Code, OpenCode та інші):

```
"Використай cot-reasoning, щоб дослідити, чому наш API повертає 500 помилок"
"Застосуй фреймворк cot-reasoning до цього архітектурного рішення"
"Використай cot-reasoning, режим BASIC, щоб розглянути цей diff на ризики"
```

### Контракт активації

| Механізм | Як працює |
|----------|-----------|
| Активація за описом | Опис у frontmatter навички (з явними NOT-умовами) автоматично маршрутизує до неї запити на багатокрокові міркування |
| Явна формулювання виклику | Згадка "cot-reasoning" у запиті активує навичку напряму, напр. "Використай cot-reasoning, щоб ..." |
| Конфігурація через ввід | Зазначте бажаний режим/патерн/тип мислення в тексті запиту, напр. "Використай режим STANDARD з патерном ReAct для дебагу цієї проблеми" |

## 🎯 Коли використовувати

### ✅ Використовуйте cot-reasoning для:

- Складних задач, що потребують багатокрокового аналізу
- Технічного дебагу і усунення несправностей
- Системної архітектури і дизайну
- Бізнес-стратегії і планування
- Рев'ю коду і оцінки якості
- Досліджень і збору інформації
- Прийняття рішень з кількома варіантами
- Аналізу кореневих причин
- Будь-яких задач, що потребують структурованого мислення

### ❌ Не використовуйте для:

- Простіх фактичних питань
- Тривіальних задач з прямою відповіддю
- Привітань і small talk
- Однослівних вводів
- Запитів коротших за 10 символів
- Пошуку доменних фактів (маршрут до відповідної доменної навички — сюди маршрутизується лише процедура міркування)

## 🏗️ Архітектура

### Основні компоненти

1. **Генератор потоку міркувань**
   - Розкладає складні задачі на логічні кроки
   - Кожен крок має єдину відповідальність і явні залежності

2. **Рушій самодіалогу**
   - Робить процес міркування прозорим і простежуваним
   - Формат: Thought → Analysis → Question → Answer → Conclusion → Decision

3. **Шар інтеграції інструментів**
   - Уможливлює операції з даними для міркування
   - Категорійна, середо-нейтральна таксономія інструментів (читання/запис файлової системи, виконання команд у shell, веб-пошук, пошук у коді)
   - Режими BASIC і MINIMAL повністю функціональні взагалі без інструментів

4. **Система відстеження результатів**
   - Веде аудиторський слід процесу міркування
   - Відстежує проміжні результати і валідацію
   - Виводи кроків — типізовані структури (v5.2.0), а не вільна проза

### Режими міркування

| Режим | Самодіалог | Інструменти | Рівень виводу | Правило вибору |
|-------|-----------|-------------|---------------|----------------|
| **MINIMAL** | Немає | Немає | Лише core, жорсткий бюджет шаблонності | Тривіальні задачі, розв'язувані у 2-3 прості кроки |
| **BASIC** | Обов'язковий | Немає | Core + Problem Analysis + Quality Metrics | У середовищі немає інструментів |
| **STANDARD** | Обов'язковий | За потреби | Повний контракт | Дефолт для більшості задач |
| **ENHANCED** | Скорочений або опущений | За потреби | Повний контракт, без фальсифікованого діалогу | Моделі зі сильним нативним міркуванням |

Вибір режиму масштабує церемонії до можливостей моделі: сильні моделі
скорочують самодіалог через ENHANCED; слабкі отримують повну структуру через
STANDARD.

### Типи мислення

| Тип | Для чого | Сильні сторони |
|-----|----------|----------------|
| **ANALYTICAL** | Структуровані задачі, аналіз даних | Точність, ґрунтовність |
| **CREATIVE** | Інновації, дизайн, брейншторм | Генерація ідей, дослідження |
| **CRITICAL** | Валідація, оцінка ризиків, QA | Виявлення вад, якість |
| **SYSTEMATIC** | Оптимізація процесів, троблшутинг | Надійність, повторюваність |
| **ETHICAL** | Політика, комплаєнс, соціальний вплив | Моральне міркування |
| **STRATEGIC** | Довгострокове планування, бізнес-стратегія | Конкурентна обізнаність |

### Патерни міркування

| Патерн | Для чого | Використання інструментів |
|--------|----------|---------------------------|
| **Zero-Shot CoT** | Прості задачі | Низьке |
| **Few-Shot CoT** | Задачі з прикладами | Низько-середнє |
| **Auto-CoT** | Нові задачі | Середнє |
| **Tree of Thoughts** | Складні рішення | Середньо-високе |
| **ReAct** | Задачі, насичені інструментами | Високе |

### Дисципліни міркування (v5.2.0)

П'ять екстерналізованих дисциплін заміщують те, чого бракує слабкій моделі —
толерантність до неоднозначності, самопоправлення, метакогніцію, інтуїцію
повноти — зовнішньою процедурою. Це процедурна дисципліна для існуючих кроків,
а не нова онтологія, і вони умовні за режимом: жодна не застосовується в MINIMAL.

| Дисципліна | Заміщує | MINIMAL | BASIC | STANDARD | ENHANCED |
|------------|---------|---------|-------|----------|----------|
| **Формалізація контракту** | толерантність до неоднозначності | — | — | так | так |
| **Типізовані виводи кроків** | контроль дрейфу у вільній формі | — | так | так | так |
| **Контур верифікації** | одноразовий fallback | — | — | так | так |
| **Гейт впевненості** | метакогніція | — | так | так | так |
| **Покриття edge-кейсів** | інтуїція повноти | — | — | так | так |

- **Формалізація контракту** — відкритий (open-ended) опис задачі перетворюється
  на закритий контракт (сутності, обмеження, вимірювані критерії успіху) до
  початку декомпозиції.
- **Типізовані виводи кроків** — очікуваний вивід кроку є типізованою
  структурою, а не прозою; порушення структури повертається в крок і вивід
  регенерується.
- **Контур верифікації** — провалена верифікація ітерує на захопленому сирому
  evidence із заявленим бюджетом (`Max Iterations`, `Exit Criteria`,
  `Escalation Policy`); повторний провал змінює стратегію, а не лише параметри.
- **Гейт впевненості** — метрика впевненості є гейтом (дефолтний поріг 7.0/10),
  а не звітом; нижче порогу потік ітерує, ескалює або питає. Жодного мовчазного
  проходження.
- **Покриття edge-кейсів** — коли задача має стани і переходи, валідаційні
  кейси виводяться покриттям графа, а не інтуїцією.

## ✅ Валідація

**Передумова:** [`jq`](https://jqlang.github.io/jq/) має бути встановлений для
JSON-валідації (валідатор друкує команду встановлення, якщо його немає).

Кожен потік міркувань можна перевірити проти контракту виводу навички
вбудованим валідатором (tier-aware: він перевіряє секції, які вимагає режим
конкретного потоку):

```bash
cd $(npx skills path cot-reasoning)

# Валідувати один markdown-потік
./scripts/validate-system-flow.sh -s flow_output.md

# Валідувати набір інженерних прикладів
./scripts/validate-system-flow.sh -j assets/system-examples.json

# Валідувати всі потоки в директорії
./scripts/validate-system-flow.sh -d ./flows/
```

### Регресійний набір

Сам валідатор захищений 22 регресійними кейсами (17 фікстур з манифестом
очікувань плюс 5 вбудованих CLI-кейсів), що покривають 99% його шаблонів
перевірок:

```bash
./scripts/run-test-flows.sh
```

### Lint узгодженості

Вирівнювання версій, валідність frontmatter, крос-референси та guard
універсальності, що відхиляє домен-специфічні терміни у вмісті навички:

```bash
./scripts/lint-consistency.sh
```

### Поведінковий eval

Механічні шари доводять, що перевірник контракту працює; поведінковий eval
доводить продуктову заяву — що модель, яка виконує навичку, генерує
конформні потоки з правильним профілем міркування. Десять еталонних промптів,
скорер і матриця результатів:

```bash
./scripts/run-behavioral-eval.sh <flows_dir> "<мітка моделі>"
```

Протокол і виміряні результати — в `assets/behavioral-eval/README.md`.
Поточний data point: Mistral Vibe agent (Mistral Large) — валідатор 10/10,
профіль 10/10.

### CI

Усі три шари верифікації (валідація прикладів, регресійний набір, lint)
запускаються в GitHub Actions на кожен push і pull request — див.
`.github/workflows/ci.yml`.
